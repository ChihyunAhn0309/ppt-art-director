# Research visuals that explain

Use this for a method, architecture or conceptual explanation within a deck. The goal is to make the important relationship visible before the audience reads every sentence. This is an original adaptation of principles from [paper-figure](https://github.com/JYS1025/paper-figure/tree/fe628d9c05fb7a3cbcb906180c602effc72ce9fb), inspected on 2026-10-02. It is not copied upstream code or a claim that its complete production workflow ran.

## Choose what the visual must show

Write a compact private contract alongside the slide content: the relationship to explain, required entities, what each mark represents, what each connection carries, what changes, what stays identifiable, and what the source leaves unknown. For example, model states belong at the nodes of a compression overview; distillation and quantization describe the operations between them. A parallel architecture needs parallel paths, even if a linear process reference looks attractive.

Choose the representation from that contract:

| Content that matters | Useful visual treatment |
|---|---|
| A transformation or architecture | Native states/components and connected operations; preserve branches, joins and separate control inputs |
| A real specimen, apparatus or failure appearance | Supplied/source image with editable region marks and precise annotations |
| Selection or correspondence | Stable item identities across views, defined rows/columns, or an explicitly scoped group |
| Spatial hierarchy or repeated computation | Matched levels or one explained repeated unit; encode dimensions only when supplied |
| An equation | Readable symbols with definitions and a source-supported interpretation or worked example |
| Measured comparisons or distributions | Appropriate native chart or reproducible scientific plot; preserve pairing, scales and uncertainty |

These are alternatives, not a list of assets to add. Use real observations when appearance is evidence. Without them, a labeled numerical contrast or schematic may explain more honestly than a generated sample. Do not invent activations, channel counts, merge operators, heatmap scores, error bars or physical dimensions. Keep a simple overview when it answers the audience's question.

## Compose and preserve meaning

Give the essential change or relationship the largest useful area. Let alignment and spacing expose grouping; avoid identical boxes when they conceal different roles. Keep labels, connectors, scientific marks and annotations editable when required. A real photograph can remain an independent image; a flattened whole-slide figure cannot be described as an editable diagram.

Inspect an applicable source figure's pixels and record which relationship its layout clarifies. Transfer that decision only when the user's method contains the same relationship. A visual draft, if used, proposes composition; the source contract decides scientific meaning. Correct beautiful but unsupported details before rebuilding.

## Review the saved slide

At final slide placement and normal viewing size, trace the main path, any required branch and any recurring item. Arrows must visibly meet the intended represented objects; valid native endpoint IDs alone are insufficient. Check set membership, overview/detail correspondence, source/output identity and the definitions of visual states. Essential distinctions should survive without hue alone. Inspect actual mathematical glyphs and the smallest required labels in each requested language.

Fix missing/reversed relationships or invented meaning first, then clarity and finishing issues. Preserve successful regions. If a suggested elaboration requires unavailable scientific detail, retain the truthful simpler explanation. Separate package checks, rendered review, app edit tests and animation playback in the validation record.

## Using the companion itself

This PPT skill supports a direct native route from the contract and inspected references. No paid image API is required. This route uses adapted principles; do not call it a completed paper-figure image-draft workflow.

When the user specifically requests execution of the companion, read the current entrypoint for the installed host. At the inspected revision, its Codex route requires a full composition image draft for new/substantial figure design, with explicit exceptions for user-requested bypass, exact supplied-raster reconstruction and local edits. Record the actual route; report unavailable tools accurately. Its Claude port uses a different default. Do not choose a different host's entrypoint merely to avoid a requirement, or introduce external API registration without a request. Statistical plotting and whole-deck planning remain outside the companion's scope.
